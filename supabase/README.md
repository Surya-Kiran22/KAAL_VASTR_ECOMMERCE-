# Supabase — Kaal Vastr

## Files

| File | Purpose |
|---|---|
| `CLEAN_SCHEMA.sql` | **The single source of truth.** Complete fresh-install schema. |
| `verify_schema.sql` | Read-only post-install checks. Run after the schema. |
| `config.toml` | Supabase CLI config. |

There is deliberately **no `migrations/` directory**. `CLEAN_SCHEMA.sql` is the
whole schema and is idempotent, so re-running it is safe. Earlier per-feature
migration files were removed because they conflicted with the app contract (see
"Design notes").

## Fresh install

1. Supabase dashboard → **SQL Editor** → **New query**
2. Paste all of `CLEAN_SCHEMA.sql` → **Run**
3. Paste all of `verify_schema.sql` → **Run**, confirm every status is `ok`
4. Sign up at `/admin/register` (creates the auth user + a `customer` profile)
5. Promote yourself:
   ```sql
   select public.promote_to_admin('you@example.com');
   ```
6. Re-run `verify_schema.sql` — check **13** must report at least one admin

## Staff accounts

From **Dashboard → Team → Send Invite**: the account is created, the invitee
confirms the emailed OTP, and only then is the role written to the database.
Equivalent by hand:

```sql
select public.set_user_role('staff@example.com', 'staff');
select public.set_user_active('staff@example.com', false);  -- disable, keep history
```

## Access model

| Table | anon | customer | staff | admin |
|---|---|---|---|---|
| `products` | read active | read active | read all | **read/write** |
| `orders` | insert (checkout) | insert | read + **update `status`** | read only |
| `order_status_history` | — | — | read | read |
| `business_settings` | read | read | read | **read/write** |
| `profiles` | — | own row | read staff/admin rows | **read/write** |
| `storage.objects` (`product-images`) | read | read | read | **write** |

Dispatch status is staff-only in **two** independent layers: a column-scoped
`grant update (status)` plus an RLS policy using `is_staff_only()`, and a
`before update` trigger that raises for anyone else. Re-running the old blanket
`grant update on orders` would silently undo the first layer — check **7** in
`verify_schema.sql` catches exactly that.

## Design notes / app contract

`src/lib/supabase.ts` depends on these, so changing them means changing the client:

- **`business_settings.id` is `text` and must be `'biz-001'`.** The client saves
  with `.eq('id', settings.id || 'biz-001')`. A `uuid` id here silently breaks
  settings saves. A `CHECK (id = 'biz-001')` constraint enforces the single row.
- **`products.id` / `orders.id` are `uuid`**, generated by the database.
- **`orders.status` ∈ `pending | confirmed | fulfilled | cancelled`** — these are
  the exact values in the dashboard's status filter and dropdown.
- **`products.variant_stock` is `jsonb` keyed `"Color|Size"`**, e.g.
  `{"Obsidian Black|S":4,"Obsidian Black|M":0}`. `null`/`{}` means the product
  uses the flat `stock` column. A colour+size absent from the map is treated as
  **0**, not as unlimited. Triggers validate the shape and keep `stock` equal to
  the sum of the variants.
- **Roles are never taken from client signup metadata.** `handle_new_user()`
  always inserts `customer`; elevation happens only via `promote_to_admin()` or
  `set_user_role()`, which keep `auth.users.raw_user_meta_data` in sync as a
  read-only cache for the client.

### Why the old migration files were deleted

`20260921000000_initial_schema.sql` declared `business_settings.id` as `uuid`.
Because the new file uses `create table if not exists`, keeping the old one would
have made Postgres skip the new definition and leave a `uuid` column behind —
breaking every settings save. The old file also granted blanket
`update on public.orders`, which contradicts staff-only dispatch. They were
replaced rather than layered.
